# 入力プレビューが元音声と異なっていた問題

## 見つかったこと

Web UI は音声ファイルを読み込んだ時点で、次の変換をしてから試聴・送信していた。

1. `AudioContext` でデコード
2. `OfflineAudioContext` で **16 kHz モノラルへ再レンダリング**
3. 16 bit PCM WAV に再エンコード

そのため「入力音声」として再生していたのは元ファイルではなく、16 kHz へ落とした再エンコード版だった。
16 kHz は 8 kHz までしか表現できず、高域が落ちる。元が 44.1 kHz / 48 kHz の録音なら、
この時点でこもった印象になり得る。

変換前後を聴き比べる目的では、比較対象が元録音と一致していなかったことになる。
この処理は以前から入っており、今回の修正で追加されたものではない。

影響範囲は Web UI のみ。`vlvc convert` などの CLI は元ファイルを直接読み、内部で 16 kHz 化する。

## 変更

- WAV / FLAC / OGG / MP3 は **元ファイルのバイト列をそのまま**試聴・アップロードに使う。
- 16 kHz モノラル化はサーバー（エンジン内部）だけで行い、プレビューには使わない。
- 波形表示だけはブラウザでデコードした第 1 チャネルを使う（元ファイルは変更しない）。
- サーバーが読めない形式（M4A など）とマイク録音は、従来どおりブラウザのデコード周波数で
  PCM WAV にする。この場合はデコードと 16 bit 量子化が入る。
- `encodeWav` を複数チャネル対応にし、ダウンミックスせずにインターリーブで書き出す。
- 入力の差し替え時に `URL.createObjectURL` を解放する。

## 確認したこと

- `node --check engine/web/static/app.js` 成功。
- Python テスト 58 件成功。
- 実音声での聴感確認は未実施（ブラウザでの再読み込みが必要）。

## 再確認の手順

1. サーバーを再起動する（`vlvc serve`）。
2. 画面を `Ctrl+F5` で再読み込みする（静的ファイルは no-store だが、念のため）。
3. 同じファイルを読み込み、入力欄の表示が
   「元ファイルをそのまま試聴・送信（加工なし）」になっていることを確認する。
4. 変換前と変換後を聴き比べる。

これで入力段階のこもりが無くなれば、残る差は変換処理・モデル由来ということになる。
