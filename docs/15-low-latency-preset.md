# 診断結果をもとに入力蓄積を短縮する試験

## 実機から受け取った記録

GPU特徴抽出を有効化したユーザーの診断JSON、27出力区間を分析した。
hop 500 / context 150 / crossfade 50 ms、40 kHz出力、ピッチ+12、warmup約591 msの条件。
ログ取得中は動作継続しており、平均値はこの記録範囲に限る。

| 指標 | 記録値 |
| --- | ---: |
| 推論時間・平均 | 103.48 ms |
| 推論時間・p95 / 最大 | 126.90 / 240.31 ms |
| ピッチ推定・平均 | 24.18 ms |
| 音声特徴抽出・平均 | 11.76 ms |
| 合成・平均 | 64.64 ms |
| 後処理・平均 | 1.98 ms |
| 入力蓄積 | 全区間700 ms |
| ブラウザ内の送信待ち | 全出力で0 ms |
| 音声応答まで・平均 | 109.40 ms |
| 推定遅延 p50 / p95 | 836.67 / 996.67 ms |
| 再生開始待ち・平均 / 最大 | 86.99 / 208.67 ms |

推論には余裕があり、固定の入力蓄積が主要な遅延要因になっている。
途中の遅い推論の後に再生待ちが残る傾向もあるため、遅延だけでなく途切れ回数も比較する。
前のCPU特徴抽出ログとは入力・ピッチなどの条件が異なるので、厳密な同一条件ベンチマークとは扱わない。
ユーザーの診断JSONそのものや音声はリポジトリに追加していない。

## 変更

Web UIの「区間プリセット」を追加した。開始前に選び、停止後に戻せる。
手動で hop/context/crossfade を編集すると「手動設定」に切り替わり、その値を維持する。
実行中はプリセットを変更できない。

| プリセット | hop | context | crossfade | 入力蓄積 | 継続区間のモデル入力長 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 従来設定 | 500 ms | 150 ms | 50 ms | 700 ms | 850 ms |
| 品質寄り低遅延・試験 | 300 ms | 150 ms | 50 ms | **500 ms** | 650 ms |
| 低遅延・試験 | 200 ms | 60 ms | 20 ms | **280 ms** | 340 ms |

3値を同じ比率で縮め、入力蓄積を **420 ms短縮**する。
20 msパケットでちょうど必要量が届く設定なので、パケット境界による追加の10 ms待ちも避けられる。
左contextを含む入力長/hopの比はどちらも1.7。ただし呼び出し回数は毎秒2回から5回になるため、
固定の推論起動コストは増える。小さい区間にしても同じ速度比で推論が速くなるとは限らない。

### 280 ms設定で品質低下があった場合

ユーザーの試聴では280 ms設定の変換品質が厳しいという報告があった。
短くした context / crossfade の影響を切り分けるため、「品質寄り低遅延・試験」を追加した。
この設定では両方を従来の150 / 50 msに戻し、hopだけ500→300 msにする。
入力蓄積は700→500 msと200 ms短縮される。画面上の280 ms設定も音質に注意する実験設定と明示する。

これは従来と同じ音質を保証するものではない。モデルが受け取る全区間長は850→650 msになり、
推論回数や継ぎ目の位置も変わるため、同じ発話で従来設定と比較する。
品質が戻らない場合は従来設定を使い、先読みをさらに削る設定は避ける。

ウォームアップは設定された区間長を使うため、新設定では280 / 340 msの代表入力を準備する。
既存のフレーム数、モデル出力長検証、クロスフェード、最終flush、待ち上限は変更していない。
debug JSON の settings.client_preset で選択名と実際の3値を確認できる。

## 試し方

```bash
git switch perf/web-onnx-cuda
git pull --ff-only
npm run dev
```

1. 前回と同じモデル・ピッチ・出力レートを選ぶ。
2. GPU化の比較条件を維持するため、「特徴抽出の高速化 → GPU / CUDA（試験）」も選ぶ。
3. 「区間プリセット → 低遅延・試験」と debug モードを選んで開始。
4. 画面で入力蓄積280 ms、debug JSONで accumulation_ms ≈ 280を確認する。
5. 推定遅延 p50 / p95、推論時間、送信待ち、再生途切れ回数を比較し、音声も試聴する。

現在の約100 msの推論時間が維持できれば、280 ms＋推論＋再生・通信分となり、
従来より数百msの短縮が見込める。これは予測であり、新設定での実モデル測定値ではない。
先読みとクロスフェードが短くなるため、発音や継ぎ目の品質が変わる可能性がある。
途切れ・音質悪化・処理不足があれば停止して「従来設定」へ戻す。

## 検証の範囲

実モデル・ONNX・GPUはクラウド環境にない。
模擬変換器で新設定の280 / 340 msウォームアップ、最初の出力タイミング、全フレーム数、
停止時のflush、プリセット切り替え・従来設定への復帰・手動編集と診断JSONを確認する。
既存の offline chunk assembly 比較テストにも20 msクロスフェードの条件を追加した。
実機での新しい推論時間、長時間の途切れ、音質と物理マイクから耳までの遅延は未検証。

検証結果: Python全101件（成功100・モデル依存スキップ1・失敗0）、Chromium13件成功。
20 msクロスフェードを追加した streaming テスト18件も成功。
ログは logs/low-latency-tests.log と logs/low-latency-browser.log（Git管理外）。
品質寄り設定についても500 / 650 msの準備形状、出力タイミング、全フレーム数、flush、
ブラウザの設定反映と診断JSONを模擬変換器で検証した。
追加後のPython全102件は成功101・スキップ1・失敗0、Chromium14件成功。
