# 09. 配信方式の選択肢（サーバー変換 / ブラウザ内変換）

「ブラウザで使う」には 3 通りある。現時点の実装は **A（この PC の Python が変換し、
ブラウザは UI）**。ここでは A / B / C のメリット・デメリットと判断基準をまとめる。

| | A. ローカル Web UI（実装済み） | B. 完全ブラウザ内推論 | C. サーバー + WebSocket 常時接続 |
| :--- | :--- | :--- | :--- |
| 変換する場所 | この PC（Python / torch） | 閲覧者のブラウザ（WebGPU / WASM） | この PC（Python） |
| ブラウザの役割 | UI・録音・再生 | UI・録音・再生・**推論** | UI・録音・再生（音声を逐次送受信） |
| 必要な導入 | Python 4.4 GB（venv + torch） | なし（モデル約 760 MB のDLのみ） | Python（A と同じ） |
| ネットワーク | 不要（localhost） | 不要（初回DLのみ） | 必要（LAN / インターネット） |
| 現状の速度 | 一括 RTF 0.27〜0.41 | 未計測（要検証） | A と同じ + 通信遅延 |
| ライブ適性 | 不可（区間 0.8〜1.3 秒） | 端末次第（要検証） | 可（GPU 次第。要作り込み） |
| 誰でも使えるか | この PC の前にいる人 | URL を配るだけで誰でも | URL + サーバー |
| 音声の外部送信 | なし | なし | あり（サーバーへ） |

## A. ローカル Web UI（現在の実装）

この PC で `python -m engine serve` を起動し、`http://127.0.0.1:8765` を開く方式。

**メリット**

- **変換品質と速度がそのまま使える**。GPU 実測で一括 RTF 0.27〜0.41（7.63 秒 → 2〜3 秒）。
  モデル差し替え・パラメータ追加・CLI との一貫性を保ちやすい。
- **実装コストが小さい**。すでに動いており、UI と API だけで完結する。
- **音声が PC の外に出ない**。localhost バインドなので LAN にも出さない。
- Python のエコシステム（numpy / torch / ONNX / 計測スクリプト）をそのまま使える。
- 失敗時の原因調査が容易（サーバーログ・`logs/web/<job_id>/job.json`）。

**デメリット**

- **使う人に環境構築が必要**（venv 4.4 GB、CUDA 版 torch 2.5 GB の配布物）。
  「URL を送って終わり」にはできない。
- **この PC が起動している必要がある**。iPad・スマホ・他 PC からは（host を開けない限り）使えない。
- Windows + NVIDIA GPU 前提の色が濃い（CPU でも動くが遅い）。
- 同時利用は 1 ジョブずつ（GPU を奪い合わないための設計）。
- **ライブ（マイク → 即時変換 → スピーカー）には未対応**。

**向いている場面**: 学内の 1 台で実証する、モデルやパラメータを詰める、検証記録を取る。

## B. 完全ブラウザ内推論（ONNX Runtime Web / WebGPU）

RVC の合成器を ONNX に書き出し、ContentVec・RMVPE（すでに ONNX）と一緒に
ブラウザ内で実行する。サーバーは不要。

**必要なもの（実測サイズ）**

| 部品 | サイズ | 備考 |
| :--- | ---: | :--- |
| ContentVec（HuBERT layer12） | 361 MB | 既存 ONNX を再利用可 |
| RMVPE（F0） | 345 MB | 既存 ONNX を再利用可 |
| RVC 合成器（つくよみ v2） | 53 MB | **ONNX 書き出しの実装が必要** |
| 合計 | **約 760 MB** | 初回のみ DL、以後は Cache API / IndexedDB |

**メリット**

- **導入ゼロ**。URL を開くだけで使える（PC・Mac・iPad・スマホ）。
  部員に配る・学祭で体験してもらう、といった用途に向く。
- **サーバー不要**。PC を起動しておく必要がなく、同時利用も端末数だけスケールする。
- **音声が端末外に出ない**（サーバー方式よりさらに閉じている）。
- 端末の GPU を使うため、**サーバーの GPU を占有しない**。
- 一度読み込めばオフラインでも動く（PWA 化可能）。

**デメリット**

- **実装コストが大きい**。RVC 合成器（weight norm・Snake 活性化・NSF の正弦波生成）の
  ONNX 書き出し、動的形状の扱い、Web Worker / AudioWorklet の実装が必要。
- **端末性能に強く依存**。WebGPU が無い環境では WASM 実行になり、実時間に届かない可能性が高い。
  スマホは発熱・電池・メモリ制限（タブが落ちる）のリスク。
- **初回 760 MB のダウンロード**。回線が細いと待たされる。ブラウザのキャッシュ容量制限にも当たりうる。
- **ブラウザ差が大きい**（WebGPU の対応状況・fp16 の可否・メモリ上限）。検証マトリクスが増える。
- モデルを差し替えるたびに ONNX 変換と再配布が必要。デバッグもブラウザ越しで難しい。
- 現行の Python 計測・検証ツール（`engine analyze` / `vlvc quality`）がそのままでは使えない。

**向いている場面**: 不特定多数に配る、端末を選ばず試してもらう、サーバーを置きたくない。

## C. サーバー + WebSocket 常時接続（ライブ向け）

ブラウザで録音した音声を WebSocket でサーバーへ送り、変換結果を逐次返して再生する。
A の拡張で、**ライブ用途の本命**。

**メリット**

- ブラウザは薄いクライアントで済み、重い処理は GPU 搭載 PC に集約できる。
- マイク → 変換 → スピーカーをブラウザだけで完結できる（デバイス選択の自由度が高い）。
- 将来、複数ブラウザからの同時接続や配信ソフト連携に拡張しやすい。

**デメリット**

- **現状の速度では成立しない**。区間あたり 0.8〜1.3 秒（ContentVec が CPU 実行）で、
  0.5 秒間隔の入力に追いつかない。まず ContentVec の GPU 実行が必要。
- LAN でも往復の遅延が加わる。Wi-Fi は不安定。
- サーバーとブラウザの両方の実装・運用が必要（A より複雑）。
- 音声がネットワークを流れるため、閉域网・認証の設計が要る。

**向いている場面**: 実際のライブで演者の声を変換する（本番）。

## 判断の目安

| 目的 | 選ぶべき方式 |
| :--- | :--- |
| 1 台で実証・パラメータ調整・検証記録 | **A**（現状のまま） |
| 部員や来場者に URL で配る / iPad で試す | **B**（段階的に） |
| 本番のライブで使う（低遅延） | **C**（まず A/B の知見で高速化） |
| とにかく早く「ブラウザで動く」を見せる | **A**（実装済み） |

## 共通の前提: ONNX 化は無駄にならない

B で必要になる「RVC 合成器の ONNX 書き出し」は、**C の高速化にもそのまま効く**。

1. 合成器を ONNX 化する（B の必須作業）
2. サーバー側を `onnxruntime-gpu` に載せ替える（C と A の高速化。ContentVec の GPU 実行）
3. 区間遅延を測り、0.5 秒未満なら C（WebSocket）を実装
4. 同じ ONNX をブラウザへ配れば B が完成

この順番なら、どこで止めても成果が残る（1 で高速化、2 でライブ判定、3 で配布）。

## 現時点の推奨

- **当面は A を主軸**にする（すでに動いており、検証記録も取れる）。
- 次に **合成器の ONNX 化 + ContentVec の GPU 実行**を実施する。
  ここで分割変換の区間遅延が 0.5 秒を切るかどうかが、ライブ（C）の可否を決める。
- B は「配布したい」という要求が出た時点で、同じ ONNX を使って着手する。
