# 境界再計算付き特徴量キャッシュ（試験）

## 何を変えたか

`VoiceConverter` の F0 / ContentVec 抽出を `extract_features()` に分離し、
ストリーム専用のキャッシュを選べるようにした。通常の変換は従来どおり全窓を計算する。
モデル重みの共有キャッシュとは別に、音声セッションごとに F0 と100 fpsへ展開した特徴量を保持する。
F0はピッチ変更前の値で保存し、毎回の合成時にピッチ変更を適用する。

キャッシュは近似であり、非因果モデルの出力を厳密に保つ高速化ではない。
既定OFFで、マイク変換と `stream-bench --feature-cache` のみ対象。
オフラインのファイル変換には適用しない。

## 再利用と更新

1. 最初の窓は全量抽出する。
2. 確定した古い特徴量を絶対10 msフレーム位置で保持し、右端のguardは未確定として残す。
3. 次の窓で、保持範囲と重なる先頭の特徴量を再利用する。
4. 新しい部分は左guardも付けて再抽出し、guardの出力は捨てて古い先頭と連結する。
5. 合成器へは、従来と同じ長さの音声・F0・特徴量を渡す。出力結合・クロスフェード・flushも維持する。

guardは `max(context, 100 ms)`。入力の先読みを縮めてヒット率を稼がない。
ContentVecは20 ms単位なので、抽出開始のスキップ量も20 ms単位へ切り下げる。
前の窓と20 msの位相が違う場合は全窓を再計算し、10 msの特徴量ずれを防ぐ。
手動設定のhopが奇数個の10 msフレームの場合、位相が交互に変わり、再利用できない場合がある。
省ける入力がない場合も新しい全窓の結果を使い、見かけだけのキャッシュヒットを計上しない。

ハイパスは従来どおり合成窓全体に適用する。ContentVecは双方向の文脈を参照し、
RMVPEや窓ごとのゼロ位相フィルターにも境界依存性がある。
guardを設けても、古い結果と新しい全窓の結果の一致や音質維持は保証できない。
合成器のattention・畳み込み・音源状態は今回キャッシュしていない。

## メモリ・異常時の扱い

保持量は現在の窓内の確定フレームだけ。セッション全体の特徴量を蓄積しない。
他セッションと共有せず、resetで音声・特徴量・カウンターを初期化する。
出力長不正や推論失敗時は、未返却音声の位置・統計と一緒に特徴量キャッシュも巻き戻す。
ウォームアップではキャッシュヒット経路も準備し、終了時にセッション状態を初期化する。
既定パディング以外、端数の入力フレーム、オフラインdenoise/dehumとの併用は対象外。

## 表示の意味

- `requested_frames`: 全窓を抽出した場合の入力フレーム数（反射パディングを含む）。
- `computed_frames`: 実際に抽出したフレーム数。境界の再計算分も含む。
- `avoided_frames`: 上記の差。画面の「抽出入力を何%省略」はこの比率。
- `reused_frames`: 古い特徴量から採用したフレーム数。guardは再計算するので省略入力数とは異なる。
- `retained_frames`: 現在保持しているフレーム数。
- `alignment_misses`: 20 msの位相違いで再利用を見送った回数。

通常表示と debug JSON の `feature_cache`、各出力記録にもカウンターを含める。
抽出入力の省略率は処理時間の短縮率ではない。
境界再計算とテンソル結合の費用があるため、実時間が改善しない可能性もある。

## 模擬バックエンドでの作業量検証

10秒入力、20 msパケット、同じ合成経路のモデル不要テストで確認した値:

| 設定 | 要求フレーム | 抽出フレーム | 省略入力 | 再利用特徴フレーム |
| --- | ---: | ---: | ---: | ---: |
| 従来700 ms | 1685 | 1613 | 72（約4.3%） | 360 |
| 品質寄り500 ms | 2179 | 2055 | 124（約5.7%） | 620 |
| 短い先読み280 ms | 1736 | 1736 | 0 | 0 |

保守的なguardなので省略量は小さい。ユーザーのGPUログではF0+ContentVecが平均約36 ms、
合成が約65 msだったため、このキャッシュだけで全遅延を大きく減らせるとは見込まない。
まず品質と実時間で再利用が成立するかを確かめるための試験である。
この表は推論時間のベンチマークではなく、実モデルの速度・品質の確認は未実施。

## 試し方

同じモデル・ピッチ・GPU設定・hop/context/crossfadeで、OFF→ONを比較する。
まず「従来設定」または「品質寄り低遅延」で試す。短い先読みではguardが大きく、効果が出ないことがある。
Web UIで「特徴量キャッシュ」とdebugをオンにし、抽出入力省略率・F0/ContentVec/合成/全推論時間、
推定遅延、途切れ回数を記録する。音質も同じ発話で比較し、悪化する場合はOFFへ戻す。

同じWAVで再現可能な比較:

```bash
python -m engine stream-bench -m models/tsukuyomi/tsukuyomi-normal1.pth \
  -i logs/verify/tts-input-ja.wav --device cuda --ort-cuda --hop 0.3 --context 0.15 --crossfade 0.05
python -m engine stream-bench -m models/tsukuyomi/tsukuyomi-normal1.pth \
  -i logs/verify/tts-input-ja.wav --device cuda --ort-cuda --hop 0.3 --context 0.15 --crossfade 0.05 --feature-cache
```
