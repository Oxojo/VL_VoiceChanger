# ストリーミング遅延の debug モード

## 使い方

```bash
npm run dev
```

1. 通常どおりモデル・デバイス・hop/context/crossfade を選ぶ。
2. 開始前に **debug モード：遅延の内訳を表示**をオンにする。
3. 「マイク変換を開始」を押して話す。計測の切り替えは停止してから行う。
4. 「診断JSONを保存」で比較用の記録を保存する。停止・エラー後にも保存できる。

GPU 試験ブランチの変更を含むが、特徴抽出は既定で CPU。
debug のために GPU を導入する必要はない。実変換には従来と同じ RVC / ONNX モデルが必要。

## 表示の意味

上部の **入力 → 再生開始予定の推定遅延**は、出力区間の先頭サンプルに対応する
AudioWorklet 入力時刻と、同じ音声の AudioBufferSource 再生開始予定時刻の差。
入出力のサンプル位置を10 ms単位のフレームに対応付け、同じ AudioContext の時計で求める。
モデル準備・マイク許可待ちは含まない。
マイク開始前の推論ウォームアップも含まない。準備時間は `settings.warmup_ms` に別記録する。

**物理マイクから耳までの実測値ではない。** 入力デバイス・OSの取り込みは測れていない。
音声グラフの量子化や入力のリサンプリングもあるので、表示の小数桁が物理的な精度を保証するものではない。

| 表示 | 範囲・種類 |
| --- | --- |
| 設定値 | サーバーでフレームに量子化した hop / context / crossfade。既定は500+150+50=700 ms |
| 入力蓄積 | 対応する出力の先頭から、今回送信済みの入力末尾までの音声時間。短い flush では700 msより短くなる |
| 入力末尾 → 送信 | 音声グラフ時刻による推定。パケット受け渡しと送信待ちを含む |
| ブラウザ内の送信待ち | パケットをメインスレッドで受け取ってから送るまでの実測。上段の内数 |
| 送信 → 音声応答 | 同じブラウザの performance.now() による実測。通信、サーバー処理、ブラウザの受信処理待ちを含む |
| サーバー内の合計 | WS受信後から、音声送信完了・ACK作成直前までの実測。socket内の受信待ちは含まない |
| サーバーの実行待ち | executor への投入からワーカー開始までの実測 |
| 推論 | その要求で実行した convert_array の合計時間。モデルロードは含まない |
| ピッチ推定・音声特徴・合成・後処理 | 推論の内数。その出力を作った要求の各段階の合計。通常表示の「全区間の平均」とは別 |
| ワーカー内の推論以外 | worker時間から推論時間を引いた値。フレーム管理・出力結合など |
| 音声応答 → 再生開始予定 | 同じ AudioContext 上の待ち。先行する再生キューや開始時の50 ms余裕を含む |
| ACK往復 | 同じブラウザ時計による要求送信からACK受信までの実測。音声応答とは別の時点 |
| ACK往復 − サーバー時間 | 通信＋ブラウザ処理などの残差。一方向の通信時間ではない |
| baseLatency / outputLatency | ブラウザ申告値。未対応の場合は「未取得」。総推定値に単純加算しない |

入力パケット20 msは入力蓄積と重なるため、700 msにさらに20 msを足すものではない。
表の行には内数・重複区間・別の時計を使った計測があるため、**すべての行を足し合わせない**。
ブラウザとサーバーの生の時刻は引き算せず、それぞれの時計で計測した時間長だけを交換する。
音声グラフと performance.now() の進み方や処理タイミングにも差があるため、分解値の和と上部の推定値が完全一致するとは限らない。

音声の応答がない蓄積中のパケットでは、ACK・処理時間だけを更新し、架空の入出力遅延を作らない。
推論が詰まった場合は、現在の待ち音声量と応答待ち経過を表示する。
待ち音声量は実際に待った時間ではなく、未返却の入力音声の長さである。

## JSONの範囲

- `settings`: モデルID、選択した設定、実際のフレーム設定と出力レート。
- `device_estimates`: ブラウザ申告の出力経路・出力デバイス遅延。未対応は null。
- `summary`: **直近最大300出力**の推定遅延 p50 / p95 / 最大。全出力の累計件数も別途記録。
- `records`: 出力先頭フレーム・フレーム数と、対応する要求の分解時間。
- `last_packet`: 最後に応答が来た要求のACK・サーバー処理時間。
- `client_state`: 保存・更新時点の待ち音声量、応答待ち経過・要求番号、状態。
- `reason`: 停止・切断・エラー理由。音声出力前の失敗も保存できる。
- `limitations`: 計測上の制約。

波形データは保存しない。JSONはブラウザから直接ダウンロードし、サーバーに診断ログや音声を追加保存しない。
モデルIDやエラー理由に含まれるファイルパスは記録に残り得るため、共有時は内容を確認する。
新しいセッションを開始すると前の診断はリセットする。再接続で要求番号と入力原点もリセットする。
統計は全パケットではなく直近の**音声出力ごと**。flush で複数チャンクが返る場合は一つの出力記録にまとめる。

## プロトコルと負荷

開始JSONに `"debug": true` を付ける。
ready の `debug` は `hop_ms / context_ms / crossfade_ms`。
ack / done の `debug` は要求番号、サーバー処理・実行待ち・ワーカー・推論時間、段階別時間、出力先頭フレームとフレーム数。
要求番号はバイナリ入力と stop の両方で1ずつ増え、最初は1。
バイナリ音声の形式と「1要求ずつACKを待つ」動作は変えない。
`debug: false` または省略では、追加の診断応答・ワーカー時計計測・Worklet時刻メタデータを付けない。

表示更新は最大約4回/秒、出力記録は300件に制限する。
ただし計測・表示・追加JSONの負荷はあるため、性能比較は同じ debug 設定で行う。
物理的なマイク→スピーカー遅延を確認するには、別途ループバックなどによる実機計測が必要。

## 検証

- Python: 全98件、成功97・モデル依存スキップ1・失敗0。
- JavaScript: 12件成功。音声フレーム対応、複数時計の分離、短いflush、記録上限・分位値、異常な応答の拒否を含む。
- Chromium: 模擬マイク・変換器で11件成功。通常モード、debug表示、120 msの入力蓄積、
  停止後のJSON保存、出力前の過負荷停止の診断保存、切断・再接続などを確認。
- ワーカーを実際に待たせ、実行待ちと推論時間を区別できることを確認。

ログは `logs/debug-mode-tests.log` と `logs/debug-mode-browser.log`（Git管理外）。
実RVCモデル・ONNX資産・GPUがないため、実モデルの音質・実測性能や物理的な音響遅延は未検証。
