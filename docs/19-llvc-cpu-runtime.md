# LLVC CPUの処理遅延を減らす

CPUで「入力に追いつかない」と停止する報告を受け、同じモデルの実行方法を変更した。
従来の13ms単位のPyTorch実行は、この環境でも1回約11〜13msで、送信・再生を加えると余裕が小さかった。
ユーザーの実行ログは未取得なので、手元での停止原因を確定したものではない。

## 変更点

- CPUはONNX RuntimeのCPUExecutionProvider・FP32・1スレッドで実行する。CUDA選択は[CUDA Graphの試験対応](20-llvc-cuda-graph.md)を参照。
- encoderの状態を各層で大きなバッファへ書き戻す実装を、一度だけ連結して返す形へ変更した。
  ONNX変換時の大きなScatterNDコピーを削減する。元の更新手順とビット単位で一致することをテストした。
- 学習済み重み・ネットワーク構造・内部13ms・入力送信20ms・再生クッション15msを維持する。
  量子化、先読み追加、入力蓄積や停止閾値の引き上げは行わない。
- 初回開始時、**実際にロードした重み**からONNXを生成し、6回の連続処理でPyTorchとの出力・全状態を比較する。
  許容誤差はFP32の相違を考慮した `rtol=1e-3 / atol=1e-4`。比較は音質評価ではない。
- 生成グラフは`models/llvc/onnx/`へ原子的に保存する。checkpointのmtime/サイズ、モデル/エクスポートコード、
  PyTorch版でキャッシュを分け、再利用時にもロードした重みとの数値比較を行う。
  壊れたキャッシュは一度作り直す。失敗時は準備エラーとし、遅い経路へ黙って戻さない。
- 実行方式と起動時の最大出力誤差をready応答、画面、debug JSONへ含める。
  LLVCで待ち行列が上限を超えた場合は、LLVC用の説明と推論RTF・送信待ち時間を表示する。

`onnx>=1.17`をengine依存へ追加した。`npm run dev`の不足依存チェックにも含めた。
インストール済みのONNX Runtime CPU機能を使い、onnxruntime-gpuの入れ替えは不要。

## 手元での反映

開発サーバーをCtrl+Cで停止してから:

```bash
git pull --ff-only
npm run dev
```

画面を更新し、「変換方式 → LLVC」「デバイス → CPU」「debugモード → ON」で開始する。
**LLVC: ONNX Runtime CPU / FP32** と表示されれば、新しい経路を使用している。
初回のONNX生成はマイク開始前に行うため、準備に数秒かかる場合がある。
重みは既存ファイルを使い、再取得は不要。Python追加依存を導入できない場合は`npm run setup`の出力を確認する。

## 検証範囲

[速度比較の生データ](benchmarks/llvc-cpu-runtime.json)は、同じ未学習重みを使った計算試験。
AMD EPYC 9V74 / CPU1スレッド / PyTorch 2.15.0+cpu / ONNX Runtime 1.31.1、FP32、4秒入力、20ms送信単位。
モデルの読込・変換・数値検証・20パケットのウォームアップは時間測定から除外した。
共有クラウド環境のため負荷で変動する。音声品質・実マイクから出力までの測定ではない。

| 指標 | 従来PyTorch | CPU ONNX |
| --- | ---: | ---: |
| 13ms分の計算 平均 | 13.08 ms | 3.92 ms |
| 13ms分の計算 p95 | 16.32 ms | 4.89 ms |
| 20msパケット処理 平均 | 20.31 ms | 6.21 ms |
| 計算RTF | 1.01 | 0.30 |

同一入力・同一重みでの最大出力差は 2.46e-06。出力長は入力と同じ64,000 samples。


Pythonは成功147・スキップ2・失敗0、JavaScript14件成功、Chromium16件成功。
encoder更新の厳密一致、逐次出力の数値一致、端数・reset、キャッシュ再利用/破損時の再生成、
不正な出力の拒否、実際のONNX経路を使ったブラウザのマイク・再生・診断JSON・停止/再開を確認した。
テスト用ネットワークは未学習であり、製品コードには未学習モデルへの代用経路がない。

Windows実機・公式学習済み重みの音質・100ms以下の物理遅延はこの環境で未検証。
ユーザーの停止が解消したかは、更新後の実際のRTFと送信/再生待ち、診断JSONで確認する必要がある。
